# 质量线

## 适用范围
- 适用于所有商业项目
- 用于判断一个任务、一个阶段、一次交付是否达到可接受质量线

## 核心立场
- 质量不是“尽量完美”，而是“在当前范围内可交付、可验证、可维护”。
- 商业项目的质量线必须同时覆盖工程正确性和交付可用性。
- 没有验证、没有边界说明、没有风险说明的结果，不算达到质量线。

## 稳定规则
- 作用域必须受控。
- 主链路必须闭环。
- 验证路径必须明确。
- 关键风险必须可见。
- 输出必须可交付给下一位人类或 agent 继续使用。

## 最低质量线

### 1. 作用域控制
- 修改范围与任务目标一致
- 没有无说明的越界改动
- 没有顺手重构无关部分

### 2. 功能闭环
- 当前任务的主目标已经成立
- 关键状态流、交互流、数据流已接通
- 不存在明显半成品逻辑

### 3. 验证
- 至少完成最小必要验证
- 验证结果真实可复述
- 没跑的验证要说明原因

### 4. 稳定性
- 无明显崩溃风险
- 无明显空指针、状态不同步、资源缺失、入口不可达问题
- 没有把高频回归点打穿

### 5. 可交付性
- 输出说明足够让别人继续接手
- 改了什么、为什么改、怎么验证、有哪些限制，必须能说清
- 不能只给“做完了”的结论

## 提高质量线的场景
以下场景应提高质量线：
- 跨模块改动
- 宿主兼容改动
- UI 与行为双改动
- 外部依赖或设备环境相关改动
- 高频交互或核心营收路径改动

提高后至少应补：
- 更完整的回归验证
- 更清晰的风险说明
- 更严格的边界检查

## 常见失败模式
- 任务看似完成，但只跑通理想主路径
- 逻辑成立，但 UI 不同步
- UI 对了，但状态流已经偏了
- 验证做了，但没有说明验证范围
- 把环境问题误说成代码已经没问题

## 复核问题
- 这次修改有没有越过任务边界
- 主链路是否已经真实闭环
- 跑了哪些验证，没跑哪些
- 当前结果能不能交给别人继续维护
- 还有哪些风险没有被解决，只是被接受了

## 什么时候用
- 进入实现前确认质量目标
- 评审前自检
- 交付前收口
- 复盘时判断为什么结果不稳

## 不适用场景
- 当前只是头脑风暴，还没进入可执行阶段
- 当前只是形成任务草案，不是验收结果
