# Android 输入法任务拆分指南

## 适用范围
- 适用于 Android 输入法项目的 task 设计
- 用于把模糊需求收敛成可执行的增量任务卡

## 核心立场
- 输入法项目天然耦合高，如果 task 不拆好，执行阶段一定扩散。
- 好 task 的标准不是“写得完整”，而是“主目标单一、修改面受控、验收路径明确”。

## 稳定规则
- 一张 task 只允许一个主目标。
- 其他内容只能为主目标服务，不能顺手带上相邻大主题。
- 每张 task 必须写清：
  - 当前问题
  - 目标能力
  - 当前实现约束
  - 非目标
  - 建议修改范围
  - 验收标准
- 没有非目标的 task，默认会失控。
- 没有验证方式的 task，不进入实现。

## 推荐拆分维度

### 1. 按问题类型拆
- 输入状态修复
- 宿主输入绑定修复
- 候选引擎 / 排序 / 学习
- 词库资产化 / 清洗 / 导入
- 键盘模式与特殊键行为
- UI 参考图对齐与视觉重构
- 设置页 / 配置项

### 2. 按风险层级拆
- 先主链路稳定
- 再兼容性
- 再视觉与交互增强
- 再性能和长期优化

### 3. 按修改面拆
- 只改 state / action
- 只改 resolver / matcher / data source
- 只改 view / layout / drawable
- 只改 test / verification path

## 好任务示例
- 修单行 enter fallback，不同时做 symbol keyboard 改造
- 做候选栏 RecyclerView 化，不同时重写词库排序
- 做 symbol 分类导航，不同时改 number keyboard
- 做 UI 参考图对齐，不同时扩充字库资产

## 坏任务信号
- 一张 task 同时写“修状态 + 扩词库 + 重做 UI + 宿主兼容”
- 目标写成“整体优化输入法”
- 背景写很多，非目标不写
- 验收只写“效果正常”
- 建议修改范围横跨 service、state、view、词库脚本、设置页、宿主 app

## 稳定任务模板要求
- 任务名称清楚，不空泛
- 任务目标是闭环能力，不是大方向口号
- 背景问题聚焦当前痛点
- 当前实现约束写清楚不能碰什么
- 非目标明确排除扩散项
- 验收标准包含功能、结构、质量三类

## 拆分判断规则
- 如果一个需求会同时动“状态层 + 词库层 + UI 层”，先拆
- 如果一个需求无法给出最小修改范围，先拆
- 如果一个需求没有稳定验证入口，先补验证 task 或收紧范围
- 如果一个需求高度依赖前置基础设施，先做前置 task

## 什么时候用
- 写下一张输入法 task
- 评估当前 task 是否过大
- 复盘一个 task 为什么失控

## 不适用场景
- 当前只是修一个明确的小 bug
- 当前项目已有强制 task 模板且已足够稳定

## 来源
- 输入法项目中的高耦合演进经验
- 多次增量 task 之后形成的稳定拆分方式
