# Android 输入法验证路径

## 适用范围
- 适用于 Android 输入法项目
- 用于实现前确认验证策略、实现后执行验证、评审前做回归检查

## 核心立场
- 输入法项目最怕“表面能弹出键盘，但行为已经悄悄偏了”。
- 验证必须按层次进行，先低噪音稳定验证，再高成本环境验证。
- 没有验证路径的任务，默认不进入完整实现阶段。

## 验证顺序
- 先做纯逻辑验证
- 再做输入绑定验证
- 再做模式切换与关键交互验证
- 最后做宿主环境和设备级验证

## 分层验证模型

### 1. 核心逻辑验证
适合验证：
- 候选匹配
- 拼音切分
- 纠错规则
- 排序与学习逻辑
- 符号/数字布局解析器
- 可见性策略
- 本地词典解析与懒加载

目标：
- 在不引入宿主和 Android 运行时噪音的情况下，先确认核心逻辑成立。

### 2. 输入绑定验证
适合验证：
- `InputConnection` 的提交与删除
- 编辑器动作回车兜底
- 单行 / 多行回车
- 选区处理
- 输入框类型行为

目标：
- 确认输入法和宿主输入框之间的最关键绑定路径没有被打穿。

### 3. UI 与状态验证
适合验证：
- 状态改变后键盘是否刷新
- 候选栏 / 拼写反馈 / 符号分类标签显示是否同步
- 大小写 / 模式 / 页码 / 分类的视觉态是否和真实状态一致
- 特殊键按压态、焦点态、选中态是否一致

目标：
- 确认 UI 不是“看着像对，状态其实错”。

### 4. 宿主和设备验证
适合验证：
- 真实宿主输入框适配
- 不同输入框类型下默认模式是否正确
- 设备安装、IME 启用/切换、系统行为
- 真机或目标平台 flavor 的行为差异

目标：
- 确认项目在真实输入法场景中可用，而不是只在本地测试中成立。

## 增量任务推荐验证顺序
- 做任务分析时先写出最小验证集
- 实现后优先跑稳定本地验证入口
- 若修改涉及输入绑定，再补输入绑定验证
- 若修改涉及 UI 参考图或特殊键交互，再做针对性交互回归
- 若修改涉及宿主兼容、设备安装或 flavor 行为，再做环境验证

## 按改动类型的最小验证集

### 状态 / 引擎 / 候选改动
至少验证：
- 核心逻辑测试
- 候选可见性与选择闭环
- 拼写缓冲区生命周期

### 输入行为 / 宿主绑定改动
至少验证：
- 删除行为
- 回车行为
- 单行回车兜底
- 选区处理
- `InputConnection` 提交路径

### 符号 / 数字 / 模式改动
至少验证：
- 模式切换
- 切页
- 分类切换
- 返回字母模式行为
- 状态重置

### UI 对齐 / 参考图任务
至少验证：
- 顶栏布局
- 候选栏可见性与裁剪
- 标识图占位
- 右侧特殊键列
- 按压 / 焦点 / 选中态
- 关键行为未回归

## 稳定验证判断
- UI 改动后必须补行为回归，不只看视觉。
- 行为改动后必须补 UI 同步检查，不只看测试通过。
- 改解析器时要验证状态消费方，不只测解析器本身。
- 改候选显示策略时，要同时看拼写反馈、候选、空态。
- 任何回车 / 删除 / 模式切换改动，都属于高风险回归点。

## 输出要求
验证结果至少要说明：
- 跑了什么
- 没跑什么
- 为什么没跑
- 哪些是实际通过
- 哪些仍是剩余风险

## 什么时候用
- 写任务验收标准前
- 开始实现前
- 实现完成后
- 评审 / 交付前

## 不适用场景
- 当前工作纯粹是文档整理
- 当前工作不涉及输入主链路、UI、宿主绑定或词典逻辑

## 来源
- Android 输入法项目中高噪音环境和低噪音稳定测试并存的长期经验
- 增量输入法模块在逻辑、绑定、UI 三层经常分开回归的实践
