# AI API 中转站任务拆分指南

- 替代文件：无

- 下次复核触发条件：完成首个 MVP task 拆分、出现任务扩散、或新增计费 / 路由 / provider 大模块时复核

## 适用范围
- 适用于 AI API 中转站启动阶段的 task 设计。
- 用于把“做一个类似 OpenRouter 的平台”收敛为可执行的增量任务。

## 核心立场
- 中转站项目天然跨协议、账号、计费、路由、后台和运维，如果 task 不拆好，一开始就会变成平台级重构。
- 好 task 的标准不是覆盖完整平台，而是主目标单一、修改面受控、验证路径明确。

## 稳定规则
- 一张 task 只允许一个主目标。
- 每张 task 必须写清：
  - 当前问题
  - 目标能力
  - 当前实现约束
  - 非目标
  - 建议修改范围
  - 验收标准
- MVP 阶段优先闭环主链路，不优先追求 provider 数量。
- 没有计费与日志验收的转发任务，默认不算完整中转站能力。
- 没有非目标的 task，默认会扩散到后台、计费和路由。

## 推荐拆分顺序
1. OpenAI-compatible 非流式 chat completions
2. 用户 API key 鉴权
3. 单 provider 适配
4. 请求日志和基础 usage 记录
5. 流式 SSE 代理
6. 基础余额 / 配额扣减
7. provider key 池
8. 模型注册和对外模型映射
9. provider fallback
10. 管理后台最小配置面
11. 限流、风控和告警

## 推荐拆分维度
### 1. 按链路层拆
- 协议入口
- provider 适配
- 模型注册
- 路由选择
- 用户鉴权
- usage 和账单
- 后台配置
- 观测和告警

### 2. 按能力风险拆
- 先非流式
- 再流式
- 再 tool calling
- 再 vision / image / reasoning 等特殊能力
- 再动态路由和高级 fallback

### 3. 按商业闭环拆
- 先记录用量
- 再扣减余额
- 再价格配置
- 再套餐和充值
- 再代理、分销或多租户

## 好任务示例
- 跑通 `/v1/chat/completions` 非流式转发到单一 provider，不同时做 stream 和后台。
- 增加用户 API key 鉴权，不同时做余额、充值和套餐。
- 增加 SSE stream 代理，不同时做 provider fallback。
- 增加模型注册表，不同时接入所有 provider。
- 增加请求日志和 usage 记录，不同时做成本报表。

## 坏任务信号
- 任务名是“做一个 OpenRouter”或“完成中转站平台”。
- 一张 task 同时包含 provider 接入、用户系统、计费、后台、路由和部署。
- 验收只写“能调用模型”。
- 非目标没有明确排除特殊能力、后台、充值、风控或多 provider。
- 修改范围横跨 controller、数据库、后台、计费、路由、部署脚本，但没有分阶段验收。

## MVP 任务模板要求
- 目标能力必须能用一条 API 请求验证。
- 非目标必须排除至少一组相邻大能力。
- 验收标准至少包含：
  - 协议兼容性
  - provider 成功 / 失败路径
  - 日志或 usage 记录
  - 安全边界
  - 回归验证

## 什么时候用
- 写 AI API 中转站项目第一批 task 时。
- 判断当前需求是否过大时。
- 从“想做类似 OpenRouter”落到 MVP 范围时。

## 不适用场景
- 当前只是普通 AI 应用的 provider SDK 调用。
- 当前任务已经由项目内 workflow 精确拆好。

## 来源
- 来自 AI API 中转站方向启动前的任务拆分预判。
- 目前状态为 candidate，尚未经过完整项目验证。

## 待验证问题
- 第一版是否应该把余额扣减和 usage 记录放在同一个 task。
- provider fallback 是否应该等到至少两个 provider 适配稳定后再做。
- 后台配置面是否需要在 MVP 首轮出现。
