# AI API 中转站架构模式

## 记忆状态

- 替代文件：无
- 上次复核：2026-05-05
- 下次复核触发条件：完成首个 MVP、接入 2 个以上 provider、或真实计费链路跑通后复核

## 适用范围
- 适用于准备搭建类似 AICodeMirror、OpenRouter 的 AI API 中转站项目。
- 适用于启动阶段的架构判断、MVP 收敛和任务拆分。
- 不适用于已经大规模运营后的计费、风控和运维细则。

## 核心立场
- AI API 中转站不是简单反向代理，而是“兼容协议 + provider 适配 + 路由 + 账号额度 + 计费审计”的组合系统。
- 启动阶段最容易失控的做法，是一开始同时做全 provider、完整后台、复杂计费和智能路由。
- 最稳的演进方式，是先跑通一个 OpenAI-compatible MVP，再逐层补 provider、计费、路由、风控和运营工具。

## 候选分层
- 协议入口层
  - OpenAI-compatible `/v1/chat/completions`
  - 非流式响应
  - 流式 SSE 响应
  - API key 鉴权
- 用户与额度层
  - 用户 API key
  - 余额或配额
  - 请求级扣费记录
  - 禁用和限流状态
- Provider 适配层
  - 上游 API key
  - 请求格式转换
  - 响应格式归一
  - 错误码映射
  - usage 字段提取
- 模型注册层
  - 对外模型名
  - 上游模型名
  - provider 归属
  - 能力标记
  - 成本价与销售价
- 路由层
  - 固定模型路由
  - provider fallback
  - key 池轮询
  - 超时和重试策略
- 审计与后台层
  - 请求日志
  - token 与金额记录
  - provider 错误统计
  - 管理员模型和 key 配置

## MVP 推荐边界
- 只支持一个主要协议入口：优先 OpenAI-compatible chat completions。
- 只接 1 到 2 个 provider，不追求一开始覆盖所有模型平台。
- 先支持文本模型，再评估 vision、tool calling、reasoning、image generation。
- 先做确定性路由，再做成本、延迟、健康度驱动的动态路由。
- 先保证扣费和日志可审计，再做复杂套餐、分销或代理商体系。

## 稳定设计判断
- 对外协议要稳定，provider 差异只能存在于适配层。
- 模型名是产品契约，不能随意直接暴露上游混乱命名。
- 计费记录应基于请求事实，不应只依赖前端或后台展示。
- stream 链路必须把输出、错误、取消、扣费统一考虑。
- key 池和用户 key 是两套不同概念，不能混在一张表里。
- provider 能力标记要保守，未知能力默认不开放。

## 常见反模式
- 把 provider 请求转换逻辑散落在 controller 中。
- 只做转发，不记录 request、usage、cost 和错误细节。
- 一开始做复杂智能路由，但没有健康检查和审计数据支撑。
- 用一个字段同时表达模型、provider、上游 key 和价格。
- 默认把所有上游错误原样暴露给用户。
- 日志里记录完整 API key 或敏感 prompt。

## 什么时候用
- 准备启动 AI API 中转站项目时。
- 写 MVP task 前。
- 评估需求是否已经超过中转站启动阶段边界时。
- 判断某个模块应该放在协议、适配、路由、计费还是后台层时。

## 不适用场景
- 当前只是调用单一 AI provider 的普通业务系统。
- 当前项目已经有成熟中转平台架构，并且项目内规则更具体。
- 当前讨论的是具体供应商最新价格、最新模型列表或临时政策。

## 待验证问题
- MVP 第一版是否需要同时支持 tool calling。
- stream 失败后的扣费策略是否应按 provider usage、估算 usage 或不扣费处理。
- provider fallback 是否会带来重复扣费和用户感知不一致。
- 模型能力标记是否需要单独版本化。
