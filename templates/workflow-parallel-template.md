# 工作流模板：并行任务

## 用途
- 这份模板用于生成项目内 `workflows/parallel_workflow.md`。
- 目标是约束多任务并行时的边界、风险检查和合并策略。
- 适合在一个项目中同时存在多个独立任务线时使用。

## 模板正文

```md
# PARALLEL WORKFLOW

当多个任务需要并行推进时，必须按此流程执行。
目标：
- 避免不同任务互相污染
- 避免同一会话同时处理多个目标
- 避免文件冲突、配置冲突、资源冲突

---

## 1. 核心原则
### 1. 单会话单任务
一个 agent 会话只处理一个任务。
禁止在同一会话中同时混做多个任务。

### 2. 单任务单文档
每个功能必须对应一张独立任务卡。
禁止多个功能共用一张模糊任务卡。

### 3. 单任务明确定义作用域
每个任务必须写清：
- 指定 module
- 允许修改范围
- 禁止修改范围
- 指定 skill
- 非目标范围

### 4. 并行优先局部，不优先全局
优先选择：
- 不同 module
- 不同目录
- 不同资源域
- 不同配置域

---

## 2. 适合并行的任务类型
更适合并行的例子：
- 不同 module 的独立功能
- 不同目录下的局部功能
- 不依赖同一核心基础层的任务

不适合直接并行的例子：
- 两个任务都改同一个页面
- 两个任务都改同一个核心基础类
- 两个任务都改同一份 Manifest 或 build 配置

---

## 3. 并行执行前检查
必须检查：
- 是否会修改相同文件
- 是否会同时修改共享配置
- 是否会同时修改共享资源
- 是否会同时依赖不同风格或不同 skill

---

## 4. 合并策略
建议按风险从低到高合并：
1. 局部 UI / 局部逻辑
2. 局部资源改动
3. 公共类改动
4. 配置改动
5. Manifest / Gradle / 全局入口改动

---

## 5. 冲突处理
如果两个任务改了同一个文件，必须先：
- 明确冲突点
- 判断冲突类型
- 给出最小合并方案
- 再决定是否需要二次调整

---

## 6. 并行任务输出要求
每个并行任务结束时，必须额外说明：
- 本任务改了哪些文件
- 是否可能与其他任务冲突
- 最可能冲突的文件有哪些
- 是否修改了共享资源或共享配置
- 合并时应优先检查什么
```
