# 工作流模板：实现执行

## 用途
- 这份模板用于生成项目内 `workflows/implementation.md`。
- 目标是约束 agent 进入实现阶段后的执行顺序，避免一上来就混改所有逻辑。

## 模板正文

```md
# IMPLEMENTATION WORKFLOW

进入实现阶段后，必须按以下流程执行。
目标：
- 先把结构搭对
- 再把功能接通
- 再把风险收口
- 最后再交付

---

## 总体原则
1. 先骨架，后逻辑
2. 先可编译，后完整
3. 先局部验证，后整体收口
4. 优先复用现有代码
5. 优先遵守指定 skill
6. 优先保持与当前 module 风格一致
7. 不做与当前任务无关的重构

---

## 阶段 A：先补可编译骨架
### 目标
先把结构必须存在的部分补齐，让工程尽快接近可编译状态。

### 优先完成的内容
- 相关类文件
- 相关布局文件
- 相关资源文件
- 相关配置文件
- 必要注册项
- 基础接线代码

### 要求
- 被引用的类必须存在
- 被引用的资源必须存在
- Manifest / 配置必须完整
- 不要求此阶段功能已全部完成
- 但要求结构已经正确、清晰、能继续往下接

---

## 阶段 B：补功能主链路
### 目标
把任务要求中的主链路功能先接通。

### 做法
优先实现：
- 主流程
- 主交互
- 关键状态流转
- 用户可见结果

### 要求
- 先保证核心链路闭环
- 不先做边角功能
- 所有逻辑必须真实接线，不能只写壳

---

## 阶段 C：补边界逻辑与稳定性
### 目标
补齐主链路之外但任务明确要求的行为，并清理明显风险。

### 重点关注
- 空状态
- 异常输入
- 边界分支
- 生命周期相关逻辑
- 空指针风险
- 状态同步问题
- 资源或配置遗漏

### 要求
- 优先处理明显会出错的边界
- 优先处理任务中已明确要求的边界行为

---

## 阶段 D：局部自检
每完成一块逻辑后，都做一次小范围检查。
检查：
- 当前改动文件是否都在允许范围内
- 是否有引用错误
- 是否有资源缺失
- 是否有明显命名不一致
- 是否有空指针风险
- 是否符合任务要求和指定 skill

发现问题时：
- 先修当前坑
- 再继续下一块

---

## 阶段 E：整体收口
### 目标
把所有实现块组合起来，确认任务已经完整闭环。

### 必须检查
- 功能之间是否互相冲突
- 状态是否统一
- 配置是否完整
- 资源是否都存在
- 入口是否可达
- 任务要求是否已覆盖
```
