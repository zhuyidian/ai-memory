# 工作流模板：任务拆解

## 用途
- 这份模板用于生成项目内 `workflows/task_breakdown.md`。
- 目标是要求 agent 在进入实现前，先完成任务理解、上下文分析、作用域确认、分阶段计划和风险预警。

## 模板正文

```md
# TASK BREAKDOWN WORKFLOW

开始任何任务时，先不要直接写代码。
必须先完成以下拆解，并在拆解完成后再进入实现阶段。

---

## 1. 任务理解
先输出：
- 任务名称
- 任务目标
- 指定 module
- 允许修改范围
- 禁止修改范围
- 指定 skill
- 核心功能点
- 非目标范围

目标：
- 确认理解的是“这次任务”，而不是凭经验自行扩展需求。

---

## 2. 项目上下文分析
先分析并输出：
- 项目整体结构摘要
- 任务涉及的 module
- 当前 module 类型
- 当前 module 中可复用的类、资源、组件、配置
- 与任务直接相关的已有实现
- 可能影响实现的依赖、配置、资源组织方式

目标：
- 找到最小改动路径，避免重复造轮子。

---

## 3. 作用域确认
明确输出：
- 这次准备修改哪些文件
- 这些文件是否都在允许范围内
- 是否存在潜在越界需求
- 如存在越界需求，最小额外改动是什么

目标：
- 防止无意修改无关模块或根工程。

---

## 4. 分阶段实施计划
将本次任务拆成 3 到 6 个阶段。
每个阶段必须输出：
- 阶段目标
- 计划修改的文件
- 关键风险
- 完成标准

建议拆法：
1. 分析
2. 骨架
3. 功能主链路
4. 边界与稳定性
5. 自检与交付

---

## 5. 风险预警
提前列出：
- 编译风险
- 配置风险
- Manifest 风险
- 资源缺失风险
- skill 冲突风险
- 架构冲突风险
- 运行时崩溃风险

目标：
- 先看到坑，再决定怎么走。

---

## 6. 进入实现前确认
只有当以上内容都输出清楚之后，才允许进入实现阶段。
如果任务描述仍不清楚，或存在明显冲突：
- 先输出问题点
- 暂不进入大规模修改
```
