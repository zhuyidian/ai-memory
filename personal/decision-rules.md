# 个人决策规则

## 适用范围
- 适用于所有项目
- 用于需求收敛、方案比较、任务拆分、交付取舍

## 核心立场
- 我做的是可收费、可复制、可交付的项目，不是纯研究型工程。
- 默认优先最小可行闭环，而不是最大理论完整性。
- 优先交付速度、风险控制、后续维护成本的平衡。

## 稳定规则
- 先判断有没有最小闭环，再判断有没有更优架构。
- 当前 task 已明确时，先执行，不重新发明 scope。
- 优先复用现有模式，除非现有模式已经明显阻碍落地。
- 能拆成两张 task，就不要揉成一张。
- 没有验证路径的“好方案”，默认不是好方案。
- 默认做最小必要改动，避免无授权大重构。
- 对用户可见收益不明显的优化，不应抢在主链路之前。
- 涉及宿主适配、平台兼容、外部依赖时，优先保守。
- 必须长期遵守的规则，写进显式文件，不只依赖 AI 记忆。

## 任务拆分规则
- 不把“状态修复、UI 重构、词库扩容、宿主兼容”混成一张任务卡。
- 一张 task 只允许一个主目标，其他内容只能为主目标服务。
- task 必须写清非目标，否则默认范围不稳。
- task 没有验收标准时，不进入实现阶段。

## 工程取舍规则
- 优先局部修改，后考虑抽象。
- 优先稳定测试入口，后考虑全量环境验证。
- 优先真实闭环，后考虑风格纯化。
- 避免为了抽象而抽象，避免为了优雅而扩散。

## 沟通规则
- 先说范围，再说方案，再说风险。
- 先指出约束，再讨论理想做法。
- 不用空泛表述替代工程事实。
- 不把“应该可以”当成验证结果。

## 什么时候用
- 需求还模糊
- 方案有多个备选
- task 需要拆分
- 需要判断“先做什么、后做什么”
- 需要决定是否值得重构

## 不适用场景
- 当前 task 已明确禁止扩散
- 项目已经有更高优先级的强约束文件
- 当前问题只是实现细节，不是决策问题

## 来源
- 来自多个任务型项目的交付经验与复盘总结
